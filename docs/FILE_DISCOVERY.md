## הכלי: `pipeline/discover.py` וה-workflow "Find the election files"

**מה הוא בודק.** בכל ריצה:

- דפים שמהם נאספים קישורים: `votes26` (כולל `/nationalresults`, `/cityresults`, `/ballotresults`), `cdn-votes26`, `media26` (דף הבית, `/files/`, ורשימת קבצים בסגנון S3: `?list-type=2`, `?prefix=files/`), `bechirot.gov.il`, דפי שיעור ההצבעה ב-gov.il, `data.gov.il` ו-`robots.txt`/`sitemap.xml`. מכל דף נאספים קישורים, קובצי הסקריפט שהוא טוען (עד שתי רמות), כתובות שמופיעות בתוך הסקריפטים (`.csv`, `.json`, `.xlsx`, `/files/`, `/api/`), ודפי חדשות שהכתובת שלהם או טקסט הקישור אליהם מדברים על הצבעה, קלפי או תוצאות (רמה אחת למטה; כתובות החדשות ב-gov.il הן לרוב מספרים). נבדקות רק כתובות בדומיין `gov.il`. מתוך סקריפטים מופיע בדוח תחת `fragment`, לקריאה ידנית, ההקשר (80 תווים לכל צד) של כל אזכור של `files/`, `turnout`, `kalpi` או `/api/`, כך שגם כתובת מורכבת מחלקים (למשל `"/files/"+"turnout_"+h+".csv"`) נראית בשלמותה.
- כתובת עם עברית או רווחים נשלחת מקודדת (`%D7%…`), ובדוח ובהצעה ל-`live_config.json` היא מופיעה בצורה המקודדת, שהיא הצורה שהפיד צריך. הצורה הקריאה מופיעה בפירוט הקובץ (`address …`). קישור פגום בדף (למשל `href="//[x/…"`) מדולג ואינו עוצר את הריצה; כתובת שלא ניתן היה לשלוח בכלל מסומנת `bad URL, not sent` ואינה נספרת ככישלון של השרת. טקסט של תגי `<meta>` (תיאור, מילות מפתח) אינו נאסף כקישור.
- במצב `full` גם שמות מנוחשים: `exp[a-z].csv`, גרסאות json/xlsx/zip של `expb`/`expc`, כ-40 שמות אפשריים לקובץ השתתפות (`turnout`, `kalpi_turnout`, `voting_percentage`, `ahuz_hatzbaa` ועוד) כ-csv/json/xlsx, עם סיומות שעה (`turnout_14.csv`, `turnout_1400.csv`), ושמות לקובצי מעטפות. כ-390 כתובות, בקצב של לכל היותר 4 בקשות בשנייה לשרת.
- במצב `quick`: הקבצים הידועים, הדפים ומה שהם מקשרים אליו, וכל כתובת שענתה עם נתונים בדוח הקודם.

**מתי הוא רץ** (שעון ישראל): כל יום 15–26.10 ב-08:43 (מ-25.10 ב-07:43); ב-27.10 כל 20 דקות מ-06:07 עד 22:47 ועוד ריצה ב-23:07, כשהריצה של :07 בכל שעה מלאה (`full`) ושתי האחרות `quick`; ב-28–29.10 פעם בשעה ב-:13 (מלאה). אפשר להפעיל חיפוש בכל עת, עם `mode` = `full` / `quick` / `auto` (ברירת מחדל `auto`). בשדה `urls` אפשר לתת כתובות נוספות, מופרדות ברווח (למשל כתובת שהוועדה פרסמה בהודעה): הן נבדקות משרת GitHub כמו כל השאר, וגם הקישורים שבהן נאספים. ל-cron אין שנה, ולכן התזמון היה חוזר בכל אוקטובר; הצעד הראשון של ה-workflow מסיים ריצה מתוזמנת מחוץ ל-15–29.10.2026 בלי לעשות דבר. אחרי 29.10 הבעלים מכבה את ה-workflow (Actions → "Find the election files" → Disable workflow) או מוחקים אותו.

<a id="request-scan"></a>**איך מבקשים חיפוש.** המפעיל (Claude ב-session) אינו יכול להפעיל workflow (`actions_run_trigger` ו-`gh workflow run` מחזירים 403), ולכן מבקש בדחיפה של `ops/request.json` לענף `ops-control`, כמתואר ב-[`ELECTION_DAY.md`, בקשות דרך ops-control](ELECTION_DAY.md#ops-control). אותה פקודה, עם `REQ` של חיפוש:

```bash
REQ='{"workflow": "discover", "mode": "full", "urls": "https://media26.bechirot.gov.il/files/x.csv"}'
git -C ../ops fetch -q origin main && git -C ../ops checkout -q -f -B ops-control origin/main \
  && python3 -c 'import json, sys, time; r = json.loads(sys.argv[1]); r["id"] = time.strftime("%Y%m%d-%H%M%S", time.gmtime()); print(json.dumps(r))' "$REQ" > ../ops/ops/request.json \
  && git -C ../ops commit -qam "ops request: $REQ" && git -C ../ops push -qf origin ops-control
```

(`../ops`: `git fetch origin main && git worktree add --detach ../ops origin/main`, פעם אחת.) כל השדות מלבד `workflow` רשות: `{"workflow": "discover"}` הוא חיפוש `auto`; `urls` הוא מחרוזת עם רווחים או רשימה, רק `http(s)`; `runner` כמו בהפעלה ידנית (למשל `"ubuntu-latest"` או `"self-hosted"`). ערך לא תקין (`mode` אחר, כתובת שאינה http(s), שדה שאינו שייך לחיפוש) הופך את הריצה לאדומה בלי חיפוש. החיפוש רץ עם הקוד של ה-commit שנדחף (לכן `ops-control` נבנה תמיד מ-`origin/main`), נכנס לאותו תור כמו ריצה מתוזמנת (ממתין לחיפוש שרץ), ומדווח ל-`ops-reports` בלבד. אחרי כחצי דקה: `actions_list` → `list_workflow_runs` עם `resource_id: discover.yml` מראה ריצה עם `event: push`; ריצות קצרות של `live.yml`, `net-check.yml` ו-`daily.yml` לאותה דחיפה מסתיימות בירוק בלי לעשות דבר. הבעלים יכול גם Actions → "Find the election files" → Run workflow.

**רק מ-`main`.** GitHub מפעיל ריצות מתוזמנות רק מהענף הראשי, ו-Run workflow (גם דרך ה-API) קיים רק ל-workflow שהקובץ שלו נמצא בו; גם בקשה ב-`ops-control` צריכה את הקובץ ב-`main`, כי הענף נבנה ממנו. כל עוד `.github/workflows/discover.yml` לא מוזג ל-`main`, החיפוש **לא רץ** בכלל, וגם אי אפשר לבקש אותו. לכן הוא צריך להיות ב-`main` לפני הריצה הראשונה (15.10 08:43). מיד אחרי המיזוג: חיפוש אחד, `{"workflow": "discover", "mode": "full"}`, ולוודא ש-`reports/latest.md` הופיע בענף `ops-reports` ושורת הביקורת עונה.

**לאן הדוח הולך.** לענף `ops-reports` בלבד: `reports/latest.md` ו-`reports/latest.json` (תמיד הדוח האחרון), ועותק לכל ריצה `reports/discover-YYYYMMDD-HHMM.{md,json}` (שעון ישראל). לא ל-`main`: כל דחיפה ל-`main` בונה את Pages מחדש, ויש מגבלה של כ-10 בניות בשעה. דחיפה ל-`ops-reports` אינה בונה את Pages. הסיכום הקצר מופיע גם בדף הריצה ב-Actions, והדוח המלא נשמר גם כ-artifact של הריצה (14 יום), כך שהוא זמין גם אם הדחיפה נכשלה.

**עותקים של הקבצים עצמם.** Claude אינו מגיע ל-gov.il, ולכן הדוח שומר גם את הבתים של כל קובץ מועמד: כל קובץ שסווג כהשתתפות או כתוצאות, וכל קובץ נתונים שלא נקרא (xls, xlsx פגום, JSON, PDF) שהכתובת שלו מדברת על הצבעה, קלפי או תוצאות. הם נשמרים ב-`reports/files/YYYYMMDD-HHMM/<קידומת SHA>-<שרת>_<שם>` באותו ענף ובאותו commit של הדוח (וגם ב-artifact של הריצה), והנתיב מופיע בדוח בטבלה "Stored files" ובפירוט הקובץ (`stored: files/…`). כללים: עד 8 MB לקובץ ו-40 MB לריצה; כל גרסה (SHA-256) נשמרת פעם אחת בלבד, גם בין ריצות; קובץ השתתפות נשמר בכל פעם שהוא משתנה, קובץ תוצאות לכל היותר פעם בשלוש שעות; וקובץ תוצאות עם מצביעים לפני 27.10 22:00 אינו נשמר (נתוני בדיקה שייקראו כתוצאות; קובץ עם אותיות של 2022 כן נשמר). נתוני ההשתתפות הרשמיים של הוועדה מותר לפרסם גם בשעות ההצבעה, ולכן שמירתם בענף הציבורי תקינה.

**איך קוראים את הדוח.**

1. **שורת הביקורת** ("Control"): `200` = השרת מגיע לוועדה. `FAILED … this runner may not reach the CEC at all` = שום שרת של הוועדה לא ענה, וכל שאר התוצאות של הריצה חסרות משמעות לגבי הוועדה. `FAILED … other CEC hosts did answer` = רק `media25` נכשל.
2. **טבלת המפתחות**: לכל מפתח ב-`live_config.json` (`results_url`, `results_url_localities`, `station_turnout_url`) ולשיעור ההצבעה הארצי: הכתובת הנוכחית, המצב שלה, הצעה להחלפה ו-`column_aliases` נדרשים. המצבים:
   - `ok`: הכתובת עונה עם הסוג הנכון והקורא של הפיד מצליח לקרוא אותה.
   - `test file`: עונה, אבל זה קובץ בדיקה (אותיות של 2022, או שורות עם מצביעים לפני 27.10 22:00). צפוי עד 27.10 22:00.
   - `test file?` (השתתפות לפי קלפי): קובץ שנראה לפני 27.10, או ש-`Last-Modified` שלו לפני 27.10. לקובץ השתתפות אין אותיות שמסגירות קובץ בדיקה, ולכן כל קובץ כזה לפני יום הבחירות נחשב בדיקה.
   - `reader fails`: עונה עם הסוג הנכון, אבל הקורא של הפיד נכשל (הסיבה בפירוט הקובץ).
   - `answers as error (404)` וכדומה: הכתובת הנוכחית אינה עונה עם נתונים.
   - `repo copy, ok` / `repo copy, reader fails`: הערך הוא נתיב במאגר (`live_input/stations.csv`, ההמרה הידנית). הקובץ נקרא מהמאגר ולא נבדק ברשת, והדוח לא מציע להחליף אותו.
   - `not set`: אין כתובת בהגדרות.
3. **"Suggested live_config.json change"**: הצעה בלבד. מאמתים לפי הסעיף הבא לפני שמעתיקים. ההצעה אף פעם אינה מצביעה על קובץ הביקורת, על קובץ עם אותיות של 2022 או אותיות לא ברורות (תוצאות), על קובץ השתתפות מלפני 27.10, או על קובץ שהקורא של הפיד נכשל בו. מועמדים כאלה מופיעים מתחת לטבלה ב-"Other candidates", והסיבה בסוגריים (`control`, `2022/test`, `letters unclear`, `before 27.10: test?`, `reader fails`). לקובץ השתתפות הדוח מציע גם את שעת הפרסום (`Per-station release time`, ראו סעיף 3 בעץ ההחלטות).
4. **שינויים מאז הדוח הקודם**: `new` (כתובת שהתחילה לענות או הופיעה לראשונה בדף), `changed` (קוד, סוג, גודל, SHA-256, `Last-Modified` או `ETag` השתנו) ו-`gone` (קובץ שענה ועכשיו לא, או קישור שנעלם). זה המקום הראשון לחפש בו קובץ חדש.
5. **סוגים** (`class`): `results-ballot` (תוצאות לפי קלפי), `results-locality` (לפי יישוב), `turnout-station` (מצביעים לפי קלפי), `turnout-locality` (השתתפות לפי יישוב), `turnout-national` (דף או קובץ עם שיעור הצבעה ארצי לפי שעות; המספרים שחולצו מופיעים בדוח, בהשתדלות), `listing` (רשימת קבצים של S3), `data-other` (קובץ נתונים שלא זוהה), `html`, `script`, `error`.
6. **טבלת השרתים**: כתובות IP (CloudFront או אחר), קודי תשובה ורמז: `S3: no such file` = השרת עונה והקובץ לא שם; `S3: access denied` = קובץ חסר כשאין הרשאת רשימה, או חסימה; `CloudFront: request could not be satisfied` או `blocked by a firewall rule` = חסימה; `Imperva bot protection` = הגנת בוטים של gov.il. `bad URL` = כתובת שלא נשלחה בכלל (פגם בקישור, לא בשרת). אחרי שלושה כישלונות רשת (אין תשובה, timeout, ניתוק) לשרת, שאר הכתובות שלו מדולגות באותה ריצה.

**הרצה ממחשב אחר** (מחשב נייד בישראל או runner עצמי): `python3 pipeline/discover.py --out disc` כותב `disc/report.md`, `disc/report.json` ו-`disc/files/…`; עם `--push` הוא גם שומר את הדוח והעותקים בענף `ops-reports` (צריך הרשאת push). numpy אינו חובה: בלעדיו הדוח לא מריץ את הקורא של הפיד על קובצי התוצאות. על קובצי ההשתתפות הוא מריץ את אותו קורא (`check_body` ו-`station_rows`) כשהוא מהודר מקוד המקור של `live_fetch.py` (הקורא עצמו אינו צריך numpy), ומציין זאת ב-`reader`. אם גם זה נכשל, הבדיקה מסומנת `reader not run`, והדוח אינו מניח דבר על מה שהקורא מקבל.

## איך מאמתים קובץ מועמד

לפני שמחליפים כתובת בהגדרות, כל התנאים האלה צריכים להתקיים בדוח:

1. **קוד 200 והסוג הנכון.** דף HTML (תחזוקה, דף שגיאה, או מעטפת של אתר שעונה 200 לכל כתובת: "same page as the site root") אינו קובץ נתונים.
2. **כותרת.** העמודות שהקורא מצפה להן קיימות, או ש-`column_aliases` בדוח ממפה אליהן. תוצאות: `סמל ישוב`, `שם ישוב`, `קלפי` (או `מספר קלפי`), `בזב`, `מצביעים`, `פסולים`, `כשרים`, ועמודה לכל רשימה. השתתפות לפי קלפי: השמות שהקורא של הפיד מכיר, כפי שהם רשומים ב-`STATION_COLS` שב-`live_fetch.py` (הדוח קורא אותם משם בכל ריצה), למשל `סמל ישוב`, `קלפי`, `מצביעים` ו-`בזב` (בלי בעלי זכות בחירה אין אחוז הצבעה, רק קצב מול 2022). קובץ עם אחוז הצבעה בלבד, בלי מספר מצביעים, צריך גם את `בזב`.
3. **מספר שורות.** ב-2022: 12,545 שורות ב-`expb.csv`, מהן 11,707 קלפיות רגילות ו-838 שורות מעטפות (`סמל ישוב` 9999) בסוף; כ-1,215 יישובים. קובץ השתתפות לפי קלפי צריך להכיל סדר גודל דומה של קלפיות רגילות. `match_2022` (חלק הקלפיות שמספרן תואם ל-2022) צפוי להיות גבוה, ו-`arab_localities` קרוב ל-155/155. קובץ הבדיקה שצד שלישי ראה ב-5.10 הכיל 16 יישובים בלבד.
4. **אותיות.** `letters 2026` = לפחות 13 מ-15 האותיות של הרשימות שבסקרים (`מחל`, `דרך`, `רק`, `אמת`, `ל`, `שס`, `ג`, `ב`, `ט`, `ודם`, `עם`, `ך`, `די`, `כן`, `זך`; אותיות `ודם` טרם אומתו מול הוועדה). `2022 (a test file?)` = קובץ בדיקה.
5. **זמנים.** `Last-Modified` מהיום והשעה הנכונים; עמודת זמן אם יש (`data_time`); SHA-256 שמשתנה בין ריצות כשהוועדה מעדכנת. ביום הבחירות לפני 22:00, כל שורת תוצאות עם מצביעים היא נתון בדיקה.
6. **הקורא של הפיד.** `reader ok` בתוצאות פירושו שהקורא של הפיד (`read_expb`, במצב הסלחני של ליל הבחירות) קרא את הקובץ, עם ה-`column_aliases` וה-`ignore_columns` שבהצעה. בהשתתפות לפי קלפי הדוח מריץ על הבתים של הקובץ את מה שהפיד עצמו מריץ על פרסום: `live_fetch.check_body` ואז `live_fetch.station_rows`, עם ה-`column_aliases` שבהצעה כשהקורא מחיל אותם. מה שהקורא מקבל (מפריד, קידוד, שמות עמודות, אחוז הצבעה בלי מספר מצביעים) נקבע רק לפי התוצאה הזו, ולא לפי כלל שכתוב בדוח. בקוד הנוכחי של `live_fetch.py` (`station_rows`) הקורא מקבל ישירות CSV ב-UTF-8 (עם BOM או בלעדיו) או ב-cp1255, עם פסיק, `;`, טאב או `|` כמפריד (לפי שורת הכותרת), ממפה כותרות לפי `column_aliases`, קורא אחוז עם סימן `%`, ובקובץ שיש בו אחוז הצבעה ו-`בזב` בלי מספר מצביעים מחשב מצביעים = אחוז × בעלי זכות. קבצים כאלה מסומנים `reader ok` ואין צורך להמיר אותם. כשהקורא נכשל, הקובץ מסומן `reader FAILS`, וההערה מצטטת את השגיאה שלו (`the feed's reader fails on this … file (…)`) ומפנה להמרה. הקורא נחשב נכשל גם כשיותר מ-1% מהשורות אינן קריאות לו (למשל מספר שנכתב `1,234`: הפיד משמיט שורה כזו), וגם כשכל אחוזי ההצבעה בקובץ הם עד 1 (שברים, `0.453`) והקורא הפך אותם לשיעור הצבעה של פחות מ-2%.
7. **פורמט.** תוצאות: הדוח מריץ את `read_expb` על כל קובץ CSV ומדווח מה יצא; JSON ו-xlsx מסומנים `reader FAILS`, ובתוצאות נדרש ממיר, כלומר שינוי קוד. השתתפות לפי קלפי: מה שהקורא של הפיד מקבל נבדק בכל ריצה (סעיף 6). קובץ שהוא נכשל בו (JSON, xlsx, UTF-16, כותרות שאינו מכיר גם אחרי `column_aliases`, מספרים שאינו קורא כמו `1,234` או `45,3`, אחוזים שנכתבו כשברים) עובר בלי שינוי קוד בהמרה ל-`live_input/stations.csv` (סעיף 3 בעץ ההחלטות). יוצאים מן הכלל: HTML, PDF ו-xls (סעיף 3, פריט 4), וקובץ עם אחוז הצבעה בלי עמודת בעלי זכות בחירה: ממנו אי אפשר לחשב מספר מצביעים, גם לא בהמרה (הדוח אומר זאת בהערה; שינוי קוד).

### 3. שיעור ההצבעה לפי קלפי (פרסום היו״ר)

מה ידוע: לפחות ארבעה פרסומים ביום הבחירות (ערוץ 12: "כל ארבע שעות"), מצרפי לכל קלפי רגילה. שעות, כתובת ופורמט לא פורסמו (נכון ל-9.10). ההודעות צפויות מהמנכ״ל בפועל, דין ליבנה, או מאתר הוועדה.

איפה קודם: בדוח, השורה `station_turnout_url` וכל שורת `turnout-station` ב-`new`. החיפוש האוטומטי מכסה שמות מנוחשים תחת `/files/` (עם סיומות שעה), קישורים ב-`votes26`/`cdn-votes26`, כתובות בתוך הסקריפטים שלהם, דפי חדשות ב-`bechirot.gov.il`, ורשימת הקבצים של `media26` אם היא פתוחה.

1. הופיע קובץ `turnout-station`: מאמתים (מספר קלפיות, `match_2022`, `arab_localities`, אחוז הצבעה סביר מול הנתון הארצי של אותה שעה, `Last-Modified` מ-27.10 אחרי שעת הפרסום).
   - `reader ok`: `station_turnout_url` = הכתובת (בצורה המקודדת שבהצעה), ו-`column_aliases` אם ההצעה כוללת אותם. כך גם בקובץ עם `;`, טאב או `|` כמפריד, או עם אחוז הצבעה ו-`בזב` בלי מספר מצביעים: הקורא קורא אותו ישירות, בלי המרה.
   - `reader FAILS` (ההערה מצטטת את השגיאה של הקורא; למשל JSON, xlsx, כותרות שהקורא אינו מכיר ואינו ממפה, מספרים כמו `1,234`, אחוזים שנכתבו כשברים): בלי שינוי קוד, **המרה ל-`live_input/stations.csv`** (למטה). חוץ מקובץ שיש בו אחוז הצבעה בלי עמודת בעלי זכות בחירה (ההערה: `a turnout % without an eligible-voters column`): אם העמודה קיימת בשם שהדוח לא זיהה, ממירים עם `--map eligible="<השם>"`; אם אין כזו, אין ממה לחשב מצביעים, וזה שינוי קוד. עד אז החלק של ההשתתפות לפי קלפי נשאר ריק (ההשתתפות הארצית ממשיכה).
   - `reader not run` (הדוח רץ במקום שבו הקורא לא נטען): ממירים את העותק השמור ובודקים את `feed_reader` בשורת ה-JSON של ההמרה, או מריצים את הדוח מחדש ב-workflow.
   - עמודת מצביעים לפי שעות (`מצביעים עד 14:00`…): הדוח (וגם ההמרה) לוקח את העמודה האחרונה; לוודא שזו השעה העדכנית.
   - **לכל פרסום** רושמים ב-`live_input/turnout.json` את `"sectors_time": "HH:MM"`, שעת החיתוך שהוועדה ציינה לפרסום הזה (למשל `"14:00"`), לא השעה שבה הקובץ הופיע: מיד כשהוועדה מודיעה על הפרסום או על שעתו, עוד לפני שהקובץ מגיע, ולכל המאוחר **באותו commit** של ההחלפה (או של ההמרה). בזמן ההצבעה הפיד מחזיק קובץ חדש שאין לו שעה משלו עד 10 דקות, ואחר כך מפרסם אותו עם השעה שבה ראה אותו לראשונה (`docs/ELECTION_DAY.md`, הכנה 6). מדור החברה הערבית מחשב את הקצב והתחזית לפי השעה הזו, ו-45 דקות טעות ב-14:00 מזיזות את התחזית בכ-10%. הדוח מציע שעה (`Per-station release time`) מעמודת הזמן שבקובץ או מהשעה שבשם הקובץ; `Last-Modified` הוא שעת ההעלאה, מאוחרת משעת החיתוך, ומוצג רק לעיון.
2. לכל פרסום כתובת משלו (שם עם שעה): מעדכנים את `station_turnout_url` בכל פרסום, באותו commit עם `sectors_time` שלו אם היא עוד לא נרשמה (commit אחד לכל פרסום, כארבעה ביום). כתובת קבועה שמתעדכנת: רק `sectors_time`, לפני כל פרסום.
3. **לא** להצביע על קובץ בדיקה: אם הכתובת כבר קיימת עם נתוני בדיקה לפני הפרסום הראשון ב-27.10, הפיד יציג אותם כאמיתיים. הדוח אינו מציע קובץ השתתפות לפני 27.10 (`test file?`), וקובעים את הכתובת רק כשהדוח מראה נתונים מ-27.10.
4. רק דף HTML: מגרד (scraper) הוא שינוי קוד; הדוח מראה את מבנה הדף. רק PDF: הזנה ידנית של 12 אלף קלפיות אינה מעשית, והחלק של ההשתתפות לפי קלפי נשאר ריק (ההשתתפות הארצית ממשיכה). xls (Excel ישן): ההמרה אינה קוראת אותו; מי שיש לו תוכנת גיליונות שומר אותו כ-xlsx או CSV, ואז ממירים.
5. הוועדה הודיעה על פרסום והדוח לא מצא אותו: מחפשים בחדשות את ההודעה ואת הכתובת, ומבקשים חיפוש `full` עם הכתובת בשדה `urls` (`{"workflow": "discover", "mode": "full", "urls": "<כתובת>"}`, [איך מבקשים חיפוש](#request-scan)). כך היא נבדקת משרת GitHub, מופיעה בדוח עם כל הבדיקות, והבתים שלה נשמרים להמרה.

**המרה ל-`live_input/stations.csv`** (הפיד כבר קורא נתיב במאגר כמו כתובת; `live_input/README.md`):

1. בדוח, בטבלה "Stored files" (או `stored: files/…` בפירוט הקובץ), הנתיב של הפרסום, למשל `files/20261027-1447/95a22aa5-media26.bechirot.gov.il_turnout_1400.json`.
2. מורידים אותו מהענף: `git fetch origin ops-reports && git show origin/ops-reports:reports/files/20261027-1447/95a22aa5-….json > /tmp/release.json` (או מה-artifact של הריצה).
3. ממירים: `python3 pipeline/discover.py --convert /tmp/release.json`. הפקודה מזהה את הפורמט (CSV עם כל מפריד וקידוד, xlsx, JSON), מוצאת את העמודות לפי שמן (או `--map ROLE=HEADER` לעמודה שלא זוהתה, למשל `--map voters="סה״כ הצביעו"`; התפקידים: `code`, `name`, `station`, `eligible`, `voters`, `percent`, `time`), קוראת מספרים כפי שייצוא כותב אותם (`45.3%`, `1,234`, `1 234`, פסיק עשרוני `45,3`, ספרות ערביות-הודיות `١٢٣٤`), מחשבת מצביעים = אחוז × בעלי זכות כשיש רק אחוז (גם כשהאחוזים כתובים כשברים, `0.453`), משאירה ריק למצביעים של קלפי שעוד לא דיווחה (תא ריק או `-`; טקסט אחר שפירושו "טרם דווח" מציינים ב-`--blank TEXT`), וכותבת `live_input/stations.csv` בכותרת `סמל ישוב,שם ישוב,קלפי,בזב,מצביעים`. בסוף היא מריצה את הקורא של הפיד על התוצאה ומדפיסה שורת JSON: `rows` (צפוי כ-11,700 ומעלה בפרסום מלא), `skipped`, `blank_voters`, `unreadable` (תאים שאינם מספר, לפי עמודה, עם דוגמאות), `voters_from_percent`, `release` (שעה מוצעת) ו-`feed_reader` (`ok: true` נדרש). **ההמרה נעצרת בלי לכתוב דבר, ביציאה 1 ועם הסבר,** כשיותר מ-1% מתאי המצביעים (או האחוז, או בעלי זכות הבחירה) של הקלפיות אינם מספר שהיא קוראת, כשאף קלפי אינה עם מספר מצביעים, או כשאין שורות קלפי: תא כזה היה נכתב ריק, והפיד היה קורא אותו כ"טרם דווח". עד 1%: הקובץ נכתב, התאים נשארים ריקים ומודפסת אזהרה. אחרי עצירה: עמודה שגויה מתקנים ב-`--map`; טקסט שאכן אומר "טרם דווח" מציינים ב-`--blank`.
4. commit אחד ל-`main`: `live_input/stations.csv`, `"station_turnout_url": "live_input/stations.csv"` ב-`pipeline/live_config.json` (בפעם הראשונה בלבד), ו-`"sectors_time"` ב-`live_input/turnout.json` (אם עוד לא נרשמה לפרסום הזה). בסבב הבא בודקים ב-`turnout.json` של הפיד ש-`sectors` קיים ואין `station_error`.
