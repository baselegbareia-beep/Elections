# יום הבחירות: נוהל הפעלה

מסמך זה מתאר את ההכנות ואת ההפעלה של לשונית "יום הבחירות" ב-27 באוקטובר 2026 (הקלפיות פתוחות 07:00–22:00; מ-25.10 ישראל בשעון חורף, UTC+2).

## איך זה עובד

- **הסקריפט:** `pipeline/live_fetch.py` מוריד את קובץ התוצאות הרשמי של ועדת הבחירות, `https://media26.bechirot.gov.il/files/expb.csv`, כל דקה, **רק מ-22:00**. עד אז הוא רק בודק שהכתובת עונה (קוד HTTP ב-`status.results_probe`, כל כעשר דקות) ולא מוריד ולא מפרסם דבר.
- **מה הוא מחשב:** סכומים לכל יישוב, ותחזית לסיום הספירה (`pipeline/live_model.py`). התחזית מבוססת על בסיס 2022 ועל ממוצע הסקרים כנקודת מוצא.
- **מה הוא כותב:** `results.json` (הספירה והתחזית; `updated_he` הוא זמן השינוי האחרון בקובץ הוועדה, לא זמן הבדיקה), `turnout.json`, `exit_polls.json`, `history.json`, `status.json` (מצב הפיד: `results_state`, `errors`, `checked_he`) ו-`state.json` (מצב פנימי: ה-SHA-256 של הקובץ האחרון שהתקבל, רשימת הקלפיות, העותק התקין האחרון של הקלטים הידניים). קובץ שלא השתנה (אותו SHA-256) אינו מתפרסם מחדש.
- **מי מריץ ואיפה זה מתפרסם:** ה-workflow `.github/workflows/live.yml` מריץ את הסקריפט בלולאה, שומר את `live/*.json` בענף `live-data` (ענף נפרד שמכיל רק את התיקייה הזו), ומבקש מה-workflow "Publish site" (`pages.yml`) לבנות את הדף מחדש: הדף מ-`main`, הנתונים החיים מ-`live-data`. הפרסום הוא דרך GitHub Pages במצב **Source: GitHub Actions**; במצב "Deploy from a branch" הנתונים החיים לא מגיעים לדף (ראו הכנה 1).
- **כותב אחד בכל רגע:** לענף `live-data` כותב או ה-workflow או המחשב המקומי (`--publish`), בשניהם באותו מחזור: fetch, reset אל קצה הענף, העתקה, commit, push. אין rebase, ולכן דחיפה שנדחתה פשוט חוזרת על עצמה ושום דבר לא נתקע.
- **מה הדף עושה:** כשקיים `live/status.json` עם נתונים, הדף עובר ממצב "הדגמה" (ליל הבחירות 2021 בסדר הספירה האמיתי, או 2022 בסדר מדומה) למצב "חי", ומתעדכן כל דקה. ביום הבחירות הוא מתעלם מקובץ תוצאות שאינו תרגול לפני 22:00.

שרתי GitHub (Azure, ארה״ב) מגיעים ל-media25. נבדק ב-9.10.2026: קובצי 2022 הורדו בהצלחה. קובצי 2026 (`media26`, דרך CloudFront) החזירו 404 לשרתי GitHub; ייתכן שהקבצים טרם הועלו, וייתכן שכתובות הענן של GitHub חסומות (צד שלישי דיווח על קובץ בדיקה שנענה מרשתות אחרות ב-5.10, עם 16 יישובים בלבד). לכן מכינים גם מחשב בישראל (ראו "אם שרתי GitHub חסומים").

## הכנות (עד 25.10)

1. **מעבר ל-Pages דרך Actions (חובה לפני 27.10).** היום Pages מוגדר "Deploy from a branch: main / (root)", ו-`index.html` בשורש מפנה ל-`site/`. כדי שהנתונים החיים יגיעו לדף:
   - Settings → Pages → Build and deployment → Source → לבחור **GitHub Actions** (במקום Deploy from a branch). לא צריך לבחור תבנית; ה-workflow `pages.yml` כבר קיים.
   - Actions → "Publish site" → Run workflow (על `main`). בסיכום הריצה צריך להופיע `Pages build_type: workflow` ו-job בשם `deploy` שרץ. אם הסיכום אומר שהמקור הוא branch, ההגדרה לא נשמרה.
   - Settings → Environments → `github-pages` → Deployment branches and tags: `main` חייב להיות מותר (GitHub ממלא זאת מראש; אם מופיע ענף אחר, להוסיף `main`). הפיד מפעיל את `pages.yml` על `main`, ולכן ענף אחר לא יעבור.
   - לפתוח את https://baselegbareia-beep.github.io/Elections/ ולוודא שהדף נטען (גם הכתובת הישנה `…/Elections/site/` ממשיכה לעבוד: היא מפנה לשורש).
   - את Pages עצמו מפעילים ידנית: ה-workflow לא יכול להפעיל אותו עם GITHUB_TOKEN. את הענף `gh-pages` הישן אפשר למחוק.
   - עד המעבר, כל ריצה של "Publish site" ושל הפיד מציגה אזהרה בולטת בסיכום (`pages_source: legacy`) ולא מפרסמת.
2. **מתגים.** Settings → Secrets and variables → Actions → Variables:
   - `LIVE_RUNNER` = `self-hosted` מעביר את כל הריצות, כולל המתוזמנות, למחשב בישראל (ראו למטה). ללא המשתנה: שרתי GitHub.
   - `LIVE_FEED_OFF` = `true` עוצר את הריצות המתוזמנות (הפעלה ידנית עדיין עובדת), למשל כשמפרסמים ממחשב נייד.
   - `"github_feed": false` ב-`pipeline/live_config.json` עוצר ריצה שכבר רצה (הלולאה קוראת את הקובץ בכל סבב) בלי לגעת בהגדרות.
3. **גודל פנקס הבוחרים.** ב-`pipeline/live_config.json`, לעדכן את `eligible` למספר בעלי זכות הבחירה הרשמי שהוועדה פרסמה (7,340,000 הוא אומדן; דווחו גם מספרים עד כ-7.56 מיליון).
4. **תרגול.** Actions → "Election day live feed" → Run workflow: לסמן `drill`, ולהגדיר `minutes` = 15 (או 30).
   - התרגול מריץ קודם את בדיקת העשן `pipeline/test_live.py` וסבב אחד במצב 2026 (שמראה בלוג אם השרת מגיע ל-media26: `results_probe`), ואז מושך את קובץ 2022 מ-media25 (או מ-`data/official` אם אינו זמין) וחושף אותו בהדרגה לאורך הדקות שהוגדרו, כך שהדף מציג ספירה מתקדמת עם הסימון "תרגול".
   - בסוף התרגול הענף `live-data` חוזר אוטומטית למצב ההתחלתי והדף נבנה מחדש. אין מה למחוק; ריצה אמיתית ממילא זורקת קובצי תרגול שנשארו.
   - במקרה הצורך: Run workflow עם `reset` מאפס את `live-data` ובונה את הדף מחדש (ההיסטוריה של הענף נמחקת). ריצה ידנית מחכה בתור עד שריצה פעילה מסתיימת; אם צריך מיד, מבטלים קודם את הריצה הפעילה (Actions → הריצה → Cancel).
5. **נגישות הוועדה משרתי GitHub.** ה-workflow "Check access to the elections committee" רץ אוטומטית כל בוקר 20–27.10 (וגם לפי דרישה) ומציג טבלה בסיכום הריצה. ב-26.10 לבדוק גם מהמחשב בישראל: `curl -sI https://media26.bechirot.gov.il/files/expb.csv | grep -iE 'HTTP|cache-control|age|last-modified'` צריך להחזיר 200, וכדאי להוריד את הקובץ ולוודא מספר שורות ואותיות 2026, לא רק קוד 200 (קובץ הבדיקה של הוועדה הכיל 16 יישובים ואותיות 2022). זמן המטמון שבכותרות קובע כמה מהר שינוי בקובץ מגיע לפיד.
6. **נתוני השתתפות לפי קלפי.** מצב נכון ל-9.10: החלטת יו״ר הוועדה מ-16.8.2026 (פרסום שיעור ההצבעה בכל קלפי רגילה לפחות ארבע פעמים ביום הבחירות); בג״ץ 60697-08-26 (17.9.2026) ביטל את החלטת המליאה מ-6.9 והשאיר על כנו את האיסור על דיווח מזוהה; לפי הדיווחים (וואלה, JNS, ערוץ 12: "כל ארבע שעות") הפרסום המצרפי לפי קלפי נותר על כנו. שעות, כתובת ופורמט טרם פורסמו. כשתתפרסם כתובת, לרשום אותה ב-`station_turnout_url` ב-26–27.10. ההודעות יגיעו מהמנכ״ל בפועל, דין ליבנה (לא מאורלי עדס), או מאתר הוועדה.
7. **פנייה ליועץ המשפטי של הוועדה** לפני 20.10, לתיאור התצוגות (ראו "כללים"). עד לתשובה, "מי מגיע לקלפי לפי ההצבעה ב-2022" מוצג רק אחרי 22:00 (`lean_during_voting: false`).

- **איסור פרסום סקרים:** מתום יום שישי 23.10 (שבת 24.10, 00:00) ועד סגירת הקלפיות (27.10, 22:00) אסור לפרסם תוצאות של סקר בחירות שלא פורסם קודם. מותר להציג סקרים שפורסמו לפני כן, רק עם הודעה בולטת שהם אינם עדכניים ואין ללמוד מהם על דפוסי הצבעה או עמדות הציבור ביום הפרסום. האתר מציג את ההודעה הזו אוטומטית בכל הלשוניות שמבוססות על סקרים, והממוצע קפוא.

## אם שרתי GitHub חסומים

ב-9.10.2026 שרת הקבצים של 2026 (`media26`, דרך CloudFront) החזיר 404 לשרתי GitHub. לפי דיווח של צד שלישי, אותו שרת עונה לרשתות אחרות. לכן מכינים מראש מחשב בישראל, באחת משתי דרכים:

1. **Runner עצמי (מומלץ):** ב-Settings → Actions → Runners → New self-hosted runner, מתקינים את ה-runner (גרסה עדכנית; Linux או macOS, לא Windows) על מחשב שיישאר דלוק ומחובר בליל הבחירות, ומריצים `./run.sh`. ואז Settings → Secrets and variables → Actions → Variables → `LIVE_RUNNER` = `self-hosted`: מרגע זה כל הריצות, כולל המתוזמנות, רצות על המחשב הזה. זה אותו תהליך בדיוק, על חיבור ישראלי. להפעלה חד-פעמית בלי המשתנה: Run workflow עם `runner` = `self-hosted`. לחזרה לשרתי GitHub: למחוק את המשתנה.
2. **סקריפט ממחשב נייד:** קודם לעצור את הפיד של GitHub (`LIVE_FEED_OFF` = `true`, או `"github_feed": false` ב-`live_config.json` ולבטל את הריצה הפעילה), כדי שלא יהיו שני כותבים.


## בדיקות שהסקריפט מבצע

- **לפני 22:00 לא מורידים:** מחוץ לתרגול, קובץ התוצאות לא נמשך ולא מתפרסם לפני 27.10 22:00; עד אז רק בדיקת זמינות של הכתובת.
- **קבצים שאינם נתונים:** גוף ריק, דף HTML או JSON במקום קובץ CSV (תחזוקה, חסימה, הגבלת קצב), גם עם BOM בתחילתו, נדחים. קובץ בלי העמודות הצפויות נדחה.
- **קובץ בלי קלפיות שנספרו:** קובץ שמכיל רק כותרת או קלפיות עם אפס מצביעים אינו מתפרסם (ב-2021 הקובץ היה ריק עד 01:01).
- **קובץ שהתכווץ:** קובץ עם פחות קלפיות שנספרו מהקודם נדחה, והתמונה האחרונה נשארת.
- **קובץ שלא השתנה:** אותו SHA-256 לא מתפרסם שוב; `updated_he` נשאר זמן השינוי האחרון.
- **שורות בלתי אפשריות:** שורה עם יותר מצביעים מבעלי זכות בחירה נזרקת, ומספר השורות שנזרקו נרשם. שורה שסכום הקולות בה אינו תואם את הכשרים, או שאינה קריאה, מדולגת ונספרת (`checks.bad_rows`); עמודה לא מספרית חדשה מטופלת כמטא-נתונים (`checks.ignored_columns`); הקובץ נדחה רק אם יותר מאחוז מהשורות פגומות.
- **רשימות לא מוכרות:** אותיות שאינן ברשימה הידועה מסוכמות ל"אחרות" ונרשמות ב-`checks.unknown_lists`.
- **קלטים ידניים:** קובץ קלט עם שגיאת JSON (או קובץ הגדרות שבור) מדווח ב-`status.errors`, והעותק התקין האחרון ממשיך לשמש.
- **תיעוד:** לכל קובץ שהתקבל נשמר SHA-256, וזמן הבדיקה האחרונה נשמר ב-`status.checked_he`.
