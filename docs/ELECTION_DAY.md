# יום הבחירות: נוהל הפעלה

מסמך זה מתאר את ההכנות ואת ההפעלה של לשונית "יום הבחירות" ב-27 באוקטובר 2026 (הקלפיות פתוחות 07:00–22:00; מ-25.10 ישראל בשעון חורף, UTC+2).

## איך זה עובד

- **הסקריפט:** `pipeline/live_fetch.py` מוריד את קובץ התוצאות הרשמי של ועדת הבחירות, `https://media26.bechirot.gov.il/files/expb.csv`, כל דקה, **רק מ-22:00**. עד אז הוא רק בודק שהכתובת עונה (קוד HTTP ב-`status.results_probe`, כל כעשר דקות) ולא מוריד ולא מפרסם דבר.
- **מה הוא מחשב:** סכומים לכל יישוב, ותחזית לסיום הספירה (`pipeline/live_model.py`). התחזית מבוססת על בסיס 2022 ועל ממוצע הסקרים כנקודת מוצא.
- **מה הוא כותב:** `results.json` (הספירה והתחזית; `updated_he` הוא זמן השינוי האחרון בקובץ הוועדה, לא זמן הבדיקה), `turnout.json`, `exit_polls.json`, `history.json`, `status.json` (מצב הפיד: `results_state`, `errors`, `checked_he`) ו-`state.json` (מצב פנימי: ה-SHA-256 של הקובץ האחרון שהתקבל, רשימת הקלפיות, העותק התקין האחרון של הקלטים הידניים). קובץ שלא השתנה (אותו SHA-256) אינו מתפרסם מחדש.
- **מי מריץ ואיפה זה מתפרסם:** ה-workflow `.github/workflows/live.yml` מריץ את הסקריפט בלולאה, שומר את `live/*.json` בענף `live-data` (ענף נפרד שמכיל רק את התיקייה הזו), ומבקש מה-workflow "Publish site" (`pages.yml`) לבנות את הדף מחדש: הדף מ-`main`, הנתונים החיים מ-`live-data`. הפרסום הוא דרך GitHub Pages במצב **Source: GitHub Actions**; במצב "Deploy from a branch" הנתונים החיים לא מגיעים לדף (ראו הכנה 1).
- **כותב אחד בכל רגע:** לענף `live-data` כותב או ה-workflow או המחשב המקומי (`--publish`), בשניהם באותו מחזור: fetch, reset אל קצה הענף, העתקה, commit, push. אין rebase, ולכן דחיפה שנדחתה פשוט חוזרת על עצמה ושום דבר לא נתקע.
- **מה הדף עושה:** כשקיים `live/status.json` עם נתונים, הדף עובר ממצב "הדגמה" (ליל הבחירות 2021 בסדר הספירה האמיתי, או 2022 בסדר מדומה) למצב "חי", ומתעדכן כל דקה. ביום הבחירות הוא מתעלם מקובץ תוצאות שאינו תרגול לפני 22:00.

שרתי GitHub (Azure, ארה״ב) מגיעים ל-media25. נבדק ב-9.10.2026: קובצי 2022 הורדו בהצלחה. קובצי 2026 (`media26`, דרך CloudFront) החזירו 404 לשרתי GitHub; ייתכן שהקבצים טרם הועלו, וייתכן שכתובות הענן של GitHub חסומות (צד שלישי דיווח על קובץ בדיקה שנענה מרשתות אחרות ב-5.10, עם 16 יישובים בלבד). לכן מכינים גם מחשב בישראל (ראו "אם שרתי GitHub חסומים").

## הכנות (עד 25.10)

1. **מעבר ל-Pages דרך Actions (חובה לפני 27.10).** היום Pages מוגדר "Deploy from a branch: main / (root)", ו-`index.html` בשורש מפנה ל-`site/`. כדי שהנתונים החיים יגיעו לדף:
   - Settings → Pages → Build and deployment → Source → לבחור **GitHub Actions** (במקום Deploy from a branch). לא צריך לבחור תבנית; ה-workflow `pages.yml` כבר קיים.
   - Actions → "Publish site" → Run workflow (על `main`). בסיכום הריצה צריכה להופיע השורה `Pages build_type: workflow (Source: GitHub Actions); deploying`, ו-job בשם `deploy` צריך לרוץ. אם הסיכום אומר `Pages deploys from a branch (build_type: legacy); nothing was deployed`, ההגדרה לא נשמרה. אם הריצה אדומה עם `The Pages source check failed (http=…)`, הבדיקה עצמה נכשלה (API, הרשאה או רשת) ולא ההגדרה: להריץ שוב, ואם זה חוזר ראו "תקלות".
   - אחרי המעבר להריץ תרגול קצר (הכנה 4) ולוודא בשורה הראשונה של הלוג שלו `pages_source=workflow`.
   - Settings → Environments → `github-pages` → Deployment branches and tags: `main` חייב להיות מותר (GitHub ממלא זאת מראש; אם מופיע ענף אחר, להוסיף `main`). הפיד מפעיל את `pages.yml` על `main`, ולכן ענף אחר לא יעבור.
   - לפתוח את https://baselegbareia-beep.github.io/Elections/ ולוודא שהדף נטען (גם הכתובת הישנה `…/Elections/site/` ממשיכה לעבוד: היא מפנה לשורש).
   - את Pages עצמו מפעילים ידנית: ה-workflow לא יכול להפעיל אותו עם GITHUB_TOKEN. את הענף `gh-pages` הישן אפשר למחוק.
   - עד המעבר, הסיכום של "Publish site" אומר `Pages deploys from a branch (build_type: legacy); nothing was deployed` והסיכום של הפיד `Pages Source is not GitHub Actions (build_type: legacy)`: הפיד ממשיך לכתוב ל-`live-data`, אבל הדף לא נפרס מחדש.
2. **מתגים.** Settings → Secrets and variables → Actions → Variables:
   - `LIVE_RUNNER` = `self-hosted` מעביר את כל הריצות, כולל המתוזמנות, למחשב בישראל (ראו למטה). ללא המשתנה: שרתי GitHub. המשתנה חל על ריצות חדשות בלבד: ריצה שכבר רצה ממשיכה על שרת GitHub עד סופה (עד 345 דקות). כדי שהמחשב בישראל ייכנס מיד, לבטל את הריצה הפעילה (Actions → הריצה → Cancel run) ואת זו שממתינה בתור אם יש; הריצה המתוזמנת הבאה (תוך 1–20 דקות) או Run workflow עם `runner` = `self-hosted` רצות עליו.
   - `LIVE_FEED_OFF` = `true` עוצר את הריצות המתוזמנות (הפעלה ידנית עדיין עובדת), למשל כשמפרסמים ממחשב נייד. גם כאן ריצה פעילה ממשיכה עד סופה: לבטל אותה.
   - `"github_feed": false` ב-`pipeline/live_config.json` עוצר ריצה שכבר רצה בלי לגעת בהגדרות: הלולאה קוראת את הקובץ בכל סבב ועוצרת בסבב הבא (עד כדקה; בלוג: `stopping`).
3. **גודל פנקס הבוחרים.** ב-`pipeline/live_config.json`, לעדכן את `eligible` למספר בעלי זכות הבחירה הרשמי שהוועדה פרסמה (7,340,000 הוא אומדן; דווחו גם מספרים עד כ-7.56 מיליון). הערך נקרא בכל סבב, כך שתיקון ביום הבחירות נכנס לתוקף תוך דקה. מ-25.10 הפיד מדווח שגיאה ב-`errors` כל עוד נשאר 7,340,000, ובליל הבחירות הוא מדווח `register exceeded` ומציג 99% (ולא "כל הקלפיות נספרו") אם סכום בעלי זכות הבחירה בקובץ הוועדה עובר את הערך.
4. **תרגול (עד 23.10).** Actions → "Election day live feed" → Run workflow: לסמן `drill`, ולהגדיר `minutes` = 15 (או 30). מ-24.10 00:00 (תחילת שקט הסקרים) ועד 27.10 22:00 ה-workflow מסרב להריץ תרגול, כי תרגול מציג בדף תחזית מלאה על בסיס הסקרים.
   - התרגול מריץ קודם את בדיקת העשן `pipeline/test_live.py` וסבב אחד במצב 2026 (שמראה בלוג אם השרת מגיע ל-media26: `results_probe`), ואז מושך את קובץ 2022 מ-media25 (או מ-`data/official` אם אינו זמין) וחושף אותו בהדרגה לאורך הדקות שהוגדרו, כך שהדף מציג ספירה מתקדמת עם הסימון "תרגול". (סבב 2026 אחד לא מפורסם רץ בתחילת כל ריצה, לא רק בתרגול: אם הסקריפט קורס, הריצה אדומה מיד.)
   - בסוף התרגול הענף `live-data` חוזר אוטומטית למצב ההתחלתי והדף נבנה מחדש. אין מה למחוק; ריצה אמיתית ממילא זורקת קובצי תרגול שנשארו.
   - במקרה הצורך: Run workflow עם `reset` מאפס את `live-data` ובונה את הדף מחדש (ההיסטוריה של הענף נמחקת). בימים ללא תזמון (עד 26.10) ריצה ידנית מחכה בתור עד שריצה פעילה מסתיימת; ב-27–29.10 ריצה שממתינה בתור מוחלפת ב-cron הבא תוך 20 דקות ונעלמת, ולכן להפעלה מיידית מבטלים קודם את הריצה הפעילה (Actions → הריצה → Cancel run).
5. **נגישות הוועדה משרתי GitHub.** ה-workflow "Check access to the elections committee" רץ אוטומטית כל בוקר 20–27.10 (וגם לפי דרישה) ומציג טבלה בסיכום הריצה. ב-26.10 לבדוק גם מהמחשב בישראל: `curl -sI https://media26.bechirot.gov.il/files/expb.csv | grep -iE 'HTTP|cache-control|age|last-modified'` צריך להחזיר 200, וכדאי להוריד את הקובץ ולוודא מספר שורות ואותיות 2026, לא רק קוד 200 (קובץ הבדיקה של הוועדה הכיל 16 יישובים ואותיות 2022). זמן המטמון שבכותרות קובע כמה מהר שינוי בקובץ מגיע לפיד.
6. **נתוני השתתפות לפי קלפי.** מצב נכון ל-9.10: החלטת יו״ר הוועדה מ-16.8.2026 (פרסום שיעור ההצבעה בכל קלפי רגילה לפחות ארבע פעמים ביום הבחירות); בג״ץ 60697-08-26 (17.9.2026) ביטל את החלטת המליאה מ-6.9 והשאיר על כנו את האיסור על דיווח מזוהה; לפי הדיווחים (וואלה, JNS, ערוץ 12: "כל ארבע שעות") הפרסום המצרפי לפי קלפי נותר על כנו. שעות, כתובת ופורמט טרם פורסמו. כשתתפרסם כתובת, לרשום אותה ב-`station_turnout_url` ב-26–27.10. ההודעות יגיעו מהמנכ״ל בפועל, דין ליבנה (לא מאורלי עדס), או מאתר הוועדה.
7. **פנייה ליועץ המשפטי של הוועדה** לפני 20.10, לתיאור התצוגות (ראו "כללים"). עד לתשובה, "מי מגיע לקלפי לפי ההצבעה ב-2022" מוצג רק אחרי 22:00 (`lean_during_voting: false`).

את קובצי `live_input/` ואת `pipeline/live_config.json` עורכים ישירות ב-GitHub (סמל העיפרון), בענף `main`. כל סבב מושך אותם מחדש, גם במצב מחשב נייד (`--publish`): הסקריפט מושך אותם מ-`origin/main` לפני כל סבב, ולכן עריכה מקומית שלהם נדרסת (מי שמעדיף לערוך במחשב מריץ עם `--no-refresh`). קובץ שנמחק נעלם מהדף בסבב הבא, וקובץ עם שגיאת JSON מדווח ב-`errors` בלי לאבד את הגרסה התקינה האחרונה. עריכה של `live_config.json` אינה מפעילה את "Official data check" (רק עריכה של קובצי הצנרת האחרים).

הדף עשוי לפגר אחרי הנתונים בכמה דקות (מטמון Pages, עד 10 דקות לפי התיעוד). הזמן שמוצג ליד "עודכן" הוא זמן הנתונים; `checked_he` ב-`status.json` הוא הבדיקה האחרונה של הפיד.

## אם שרתי GitHub חסומים

ב-9.10.2026 שרת הקבצים של 2026 (`media26`, דרך CloudFront) החזיר 404 לשרתי GitHub. לפי דיווח של צד שלישי, אותו שרת עונה לרשתות אחרות. לכן מכינים מראש מחשב בישראל, באחת משתי דרכים:

1. **Runner עצמי (מומלץ):** ב-Settings → Actions → Runners → New self-hosted runner, מתקינים את ה-runner (גרסה עדכנית; Linux או macOS, לא Windows) על מחשב שיישאר דלוק ומחובר בליל הבחירות, ומריצים `./run.sh`. על המחשב צריך `python3` (גרסה 3.9 ומעלה) עם numpy (`python3 -m pip install numpy`, ובאובונטו גם `sudo apt install python3-numpy` מתאים): ה-workflow אינו מתקין פייתון על runner עצמי. ואז Settings → Secrets and variables → Actions → Variables → `LIVE_RUNNER` = `self-hosted`: מרגע זה ריצות חדשות, כולל המתוזמנות, רצות על המחשב הזה. ריצה שכבר רצה ממשיכה על שרת GitHub עד סופה (עד 345 דקות), ולכן לבטל אותה ואת הממתינה בתור (Actions → הריצה → Cancel run); הריצה הבאה (תוך 1–20 דקות, או Run workflow) רצה על המחשב בישראל. זה אותו תהליך בדיוק, על חיבור ישראלי. להפעלה חד-פעמית בלי המשתנה: Run workflow עם `runner` = `self-hosted`. לחזרה לשרתי GitHub: למחוק את המשתנה. לפני 23.10 להריץ תרגול אחד עם `runner` = `self-hosted` ולראות בלוג `runner=… (Linux)` (או macOS) ו-`results_probe` עם קוד 200.
2. **סקריפט ממחשב נייד:** קודם לעצור את הפיד של GitHub (`LIVE_FEED_OFF` = `true`, או `"github_feed": false` ב-`live_config.json`, ולבטל את הריצה הפעילה ואת הממתינה), כדי שלא יהיו שני כותבים.

```bash
git clone https://github.com/baselegbareia-beep/Elections && cd Elections
python3 -m pip install numpy
gh auth login                                  # או: export GH_TOKEN=<token עם הרשאת actions>
python3 pipeline/live_fetch.py --out live --loop 60 --publish
```

הסקריפט רץ עד שעוצרים אותו (Ctrl-C; `--minutes N` עוצר אחרי N דקות). הוא מושך כל דקה, שומר את `live/*.json` בענף `live-data` (דרך תיקיית עבודה `.live-data`, באותו מחזור fetch-reset-commit-push כמו ה-workflow) ומבקש מ-"Publish site" לבנות את הדף (`gh workflow run pages.yml --ref main`, ובלי `gh` דרך ה-API עם `GH_TOKEN`), לכל היותר פעם ב-50 שניות ורק כשמשהו השתנה. לפני כל סבב הוא מושך את `live_input/` ואת `pipeline/live_config.json` מ-`origin/main`, כך שעריכות ב-GitHub מגיעות לדף גם במצב הזה (ועריכות מקומיות של הקבצים האלה נדרסות; `--no-refresh` משאיר אותן, ואז עורכים במחשב). שגיאת משיכה מדווחת ב-`errors`. צריך הרשאת push למאגר. השורה שהסקריפט מדפיס בכל סבב מראה `published` ו-`dispatched`.

את הבדיקה כדאי לחזור עליה מהמחשב שנבחר כבר עכשיו: `curl -I https://media26.bechirot.gov.il/files/expc.csv` צריך להחזיר 200.

## תקלות

- **הדף לא מתעדכן:** לבדוק ב-Actions שריצת "Election day live feed" פעילה ושריצות "Publish site" מופעלות ממנה (אחת לכמה דקות). אם סיכום "Publish site" אומר `Pages deploys from a branch (build_type: legacy); nothing was deployed`, מקור ה-Pages לא הוחלף (הכנה 1). אם הריצה אדומה עם `The Pages source check failed (http=…)`, הבדיקה עצמה נכשלה (API, הרשאה או רשת) ולא ההגדרה: המשיכה הבאה מנסה שוב; אם זה נמשך אחרי שהמקור כבר הוחלף, Settings → Secrets and variables → Actions → Variables → `PAGES_DEPLOY_ANYWAY` = `true` מדלג על הבדיקה (למחוק אחרי הבחירות). ב-`live/status.json` שבענף `live-data`: `results_state`, `errors`, `results_probe`, ו-`pages_source` (`workflow` תקין, `legacy` לא הוחלף, `error` הבדיקה נכשלה).
- **הסקריפט קורס:** ריצת הפיד מסמנת `::error::` בלוג ובסיכום, ואחרי שלוש קריסות רצופות הופכת לאדומה; הריצה שממתינה בתור מתחילה מחדש מ-`main`. כל ריצה גם מתחילה בסבב אחד לא מפורסם שמפיל אותה מיד אם הקוד או ההתקנה שבורים. תיקון: לתקן ב-`main` ולהריץ Run workflow.
- **קובץ 2026 במבנה לא צפוי:** `results_state: waiting` עם `missing columns` או `rows unreadable or inconsistent` ב-`errors`. הקורא כבר מתעלם מעמודה שכותרתה אינה 1–4 אותיות עבריות, מעמודה שרובה אינו מספרים ומעמודת סכום או אחוז אחת, ומקבל את הכתיב סמל יישוב / שם יישוב. אם זה לא מספיק, בלי שינוי קוד: `ignore_columns` (רשימת כותרות להתעלמות, למשל `["סהכ"]`) ו-`column_aliases` (`{"השם אצלם": "השם הצפוי"}`, למשל `{"מס' קלפי": "קלפי"}`) ב-`pipeline/live_config.json`; הסבב הבא קורא אותם. `checks.ignored_columns` ב-`results.json` מראה מה הושמט.
- **הקובץ של הוועדה נראה לא עקבי:** `"projection_paused": true` ו-`pause_reason` ב-`live_config.json` מסתירים את התחזית ומשאירים את הספירה. המתג נכנס לתוקף בסבב הבא על הקובץ האחרון שהתקבל, גם אם קובץ הוועדה לא השתנה או נדחה מאז.
- **`register exceeded` ב-`errors`:** נספרו יותר בעלי זכות בחירה מ-`eligible` שבהגדרות; הדף מציג 99% ולא "כל הקלפיות נספרו" עד שמעדכנים את הערך (הכנה 3; נכנס לתוקף בסבב הבא).
- **להתחיל מחדש:** Run workflow עם `reset` (אחרי ביטול הריצה הפעילה). הענף חוזר למצב ההתחלתי והדף נבנה מחדש.
- **חזרה ממדגם או מדיווח:** לרוקן את הקובץ (`{}`) או למחוק אותו ב-`live_input/`; הכרטיס נעלם בסבב הבא.

## בדיקות שהסקריפט מבצע

- **לפני 22:00 לא מורידים:** מחוץ לתרגול, קובץ התוצאות לא נמשך ולא מתפרסם לפני 27.10 22:00; עד אז רק בדיקת זמינות של הכתובת.
- **קבצים שאינם נתונים:** גוף ריק, דף HTML או JSON במקום קובץ CSV (תחזוקה, חסימה, הגבלת קצב), גם עם BOM בתחילתו, נדחים. קובץ בלי העמודות הצפויות נדחה.
- **קובץ בלי קלפיות שנספרו:** קובץ שמכיל רק כותרת או קלפיות עם אפס מצביעים אינו מתפרסם (ב-2021 הקובץ היה ריק עד 01:01).
- **קובץ שהתכווץ:** קובץ עם פחות קלפיות שנספרו מהקודם נדחה, והתמונה האחרונה נשארת.
- **קובץ שלא השתנה:** אותו SHA-256 לא מתפרסם שוב; `updated_he` נשאר זמן השינוי האחרון.
- **שורות בלתי אפשריות:** שורה עם יותר מצביעים מבעלי זכות בחירה נזרקת, ומספר השורות שנזרקו נרשם. שורה שסכום הקולות בה אינו תואם את הכשרים, או שאינה קריאה, מדולגת ונספרת (`checks.bad_rows`); הקובץ נדחה רק אם יותר מאחוז מהשורות פגומות.
- **מבנה הקובץ:** עמודה שכותרתה אינה אותיות רשימה (1–4 אותיות עבריות), עמודה שרובה אינו מספרים, ועמודת סכום או אחוז אחת שמקלקלת את בדיקת הסכום מטופלות כמטא-נתונים (`checks.ignored_columns`); הכתיב סמל יישוב / שם יישוב מתקבל; `ignore_columns` ו-`column_aliases` ב-`live_config.json` מוסיפים לכך בלי שינוי קוד.
- **רשימות לא מוכרות:** אותיות שאינן ברשימה הידועה מסוכמות ל"אחרות" ונרשמות ב-`checks.unknown_lists`.
- **פנקס הבוחרים:** אם סכום בעלי זכות הבחירה בקלפיות שנספרו עובר את `eligible`, ההיקף מוצג כ-99% ומדווח `register exceeded` (ולא "כל הקלפיות נספרו"). מ-25.10 מדווח גם כל עוד `eligible` נשאר האומדן 7,340,000.
- **קלטים ידניים:** קובץ קלט עם שגיאת JSON (או קובץ הגדרות שבור) מדווח ב-`status.errors`, והעותק התקין האחרון ממשיך לשמש; `election_day` או `eligible` שאינם תקינים נופלים לברירת המחדל ומדווחים. שעה או ערך שגויים ב-`turnout.json` מדווחים ולא מתפרסמים.
- **מתגי המפעיל:** `projection_paused`, `pause_reason` ו-`envelopes_expected` נכנסים לתוקף בסבב הבא על הקובץ האחרון שהתקבל, בלי להזיז את זמן הנתונים ובלי שורה חדשה בהיסטוריה.
- **תיעוד:** לכל קובץ שהתקבל נשמר SHA-256, וזמן הבדיקה האחרונה נשמר ב-`status.checked_he`.
